# gyit progressive repository plan

Draft for discussion, 2026-09-27. This document proposes a major storage and
ingestion change; it does not authorize implementation. Native Git command
compatibility is explicitly outside this design round.

**1. Outcome and constraints**

Make a requested revision browsable before its full history is downloaded.
Serve directory traversal from filesystem metadata prepared for that purpose.
Continue importing history in the background, and incorporate later upstream
changes incrementally without disturbing mounted readers.

The design must preserve:

- Read-only mounts from many instances, with one durable-store writer.
- Atomic compare-and-swap publication and immutable data for existing readers.
- Exact names, types, modes and sizes; unknown data must never masquerade as
  an empty directory, zero-length file or missing path.
- File contents fetched on demand by readers. Mounting must not download a
  complete repository to the reader's machine.
- Stable path-based inode numbers across checkout changes. Inodes must not
  depend on object IDs, metadata block locations or publication generations.
- One globally bounded uncompressed mmap disk cache. Retain the existing
  4 GiB default and 20 GiB free-space reserve. Durable data is not cache and
  must not be evicted by that limit.
- Native GCS and local filesystem store adapters, retaining the existing S3
  abstraction and adapter. GCS is the initial cloud benchmark target, not a
  decision to drop S3. In the macOS app durable storage and cache can reside
  on local disk, in separate locations.
- Protobuf for structured durable data and control messages, generated by Buf.
- Apple Silicon only for macOS; Linux remains the initial virtio-fs target.

Full reachable commit/tree history remains a requirement. Shallow acquisition
is a scheduling optimization, not permanent truncation. Historical-blob backfill
policy is recorded once in section 13; this plan does not silently disable it.

**2. What the measurements establish**

The existing medium fixture has 9,358 entries and 957 directories. On GCE with
nested KVM and real GCS, cold scans took 70–72 seconds, with 3,120 adapter reads
for 17.4 MB. Existing-cache first scans took 0.60–0.66 seconds, but repeated
scans remained roughly 3.2–5.4 times slower than virtiofsd. See
[SCAN_PERFORMANCE.md](SCAN_PERFORMANCE.md).

There are two problems to address independently:

- Cold traversal follows Git object indexes, tree recipes and delta payloads,
  producing many small dependent network reads.
- Repeated traversal still crosses the filesystem transport. Directory opens
  currently do not request kernel directory caching. Its contribution is a
  hypothesis to measure, not an established explanation for the entire gap.

The new format should remove Git tree reconstruction from ordinary filesystem
metadata reads. Increasing concurrency alone is not the proposed solution.

Fresh GitHub clone measurements on this Mac, at Linux commit
`d266640c6c760c9bc215bf5a3ece122ca488b6f5`:

| Acquisition | Wall time | Pack bytes | Result |
|---|---|---|---|
| `git clone --bare --depth=1 --filter=blob:none` | 1.04 s | 3,098,977 | 1 commit, 6,277 trees, no blobs |
| `git clone --depth=1` | 23.23 s | 295,828,016 | Snapshot contents plus working-tree checkout |

These are single samples, not latency guarantees. The second includes checkout
and encountered case-colliding paths on the Mac filesystem; all Git objects were
retained. Use a case-sensitive checkout for correctness comparisons. The agreed
first-use target is roughly one second to names and roughly 23 seconds to a fully
available current snapshot, including filesystem metadata preparation/publication
but excluding history, on comparable hardware and network. Report object-store
upload time separately within that end-to-end total; do not quietly exclude it.

The independent review also measured a Linux tree-API traversal at 4.6 seconds,
21 requests and about 34 MB of uncompressed JSON. This is reported evidence,
not a repeat of our clone measurement. Its observed truncation did not match
documented numeric thresholds. Preserve the reproducible experiment in
[scripts/probe_tree_api.py](scripts/probe_tree_api.py) and its
[offline tests](scripts/test_probe_tree_api.py). Branch-tip pack reuse may help
these results; historical commits and GCE network conditions still need testing.

**3. Terms and separate readiness states**

| Term | Meaning |
|---|---|
| Repository | One upstream identity with shared objects, refs and ingestion state across revisions. |
| Snapshot | The immutable worktree identified by a commit and its root tree. |
| Publication | Publishing a catalog generation, using the terminology in OBJECT_STORE.md. It can add availability without changing a mounted snapshot. |
| Directory metadata | A complete listing of direct children and their known attributes, independent of file contents. |
| Metadata page | A small immutable unit of metadata reuse and copy-on-write updates. |
| Metadata container | An immutable storage object grouping independently readable pages for efficient transfer. Its target size is not a minimum rewrite size. |
| History frontier | The known boundary between ingested commits and their unavailable parents. |
| Ref observation | A captured set of ref names and object IDs against which completeness is evaluated. |
| Durable store | Repository objects, metadata indexes, publications and ingestion checkpoints. |
| Cache | Discardable decoded data that can be reconstructed from durable storage. |

Readiness is multidimensional: directory names, exact attributes, object bodies
and history coverage become available independently. Do not collapse these into
one `imported` boolean. Completeness is relative to a ref observation, not an
upstream branch that keeps moving.

A mount pins its commit. Background hydration increases available data for that
commit; observing a newer branch tip does not silently switch the mount.

**4. Initial mount and foreground demand**

For a snapshot already represented in durable storage, read its small manifest
and root directory block. This path must not contact GitHub or load the history
index. Keep root bootstrap metadata small and directly addressable.

For a repository or revision never imported:

1. Resolve only the requested branch, tag or commit and pin its exact object ID.
   Delay enumeration and fetching of other refs until after initial browsing.
2. Fetch the requested snapshot's complete trees with depth one and `blob:none`.
   The measured Linux result supports this simpler bootstrap; do not implement
   a separate `tree:1` root-only path without evidence that it is needed.
3. Persist that result and expose directory names as soon as possible. All Git
   trees are present, but prepared filesystem pages and exact sizes may not be.
   Obtain exact attributes using the policy in section 5.
4. Prioritize directory and file requests from users ahead of background work.
   Fetch missing trees or blobs in batches, coalescing requests from all readers.
5. Prepare the selected snapshot's metadata and acquire its remaining contents
   in the background, followed by full history. Readers still fetch only what
   they access from durable storage; the writer handles snapshot acquisition.

Capability-check filtered fetches and object-ID wants. If filtering is rejected,
fall back explicitly to an unfiltered depth-one fetch, with slower startup shown
in progress. Test arbitrary historical revisions as well as current branch tips.
Do not expose a pack before its required objects and delta dependencies are usable.

Preserve the existing 10-second setup behavior: complete a fast setup inline;
otherwise expose the progress `NOTICE`, with touch-to-retry. Replace it when
the root can be served correctly, rather than waiting for complete history.
Afterward, background progress belongs in app/control status. Missing attributes,
contents or not-yet-built pages wait or return a real error; never substitute an
empty directory or invented sizes. Submodule entries intentionally appear as
empty directories representing gitlinks, without mounting another repository.

Treat names-only enumeration as a transport feature to prove. On READDIRPLUS,
unknown attributes must not be inserted into the kernel as valid: test entries
with `nodeid=0` or use plain READDIR where supported. Lookup/stat still waits for
exact attributes. Measure actual `ls`, `ls -al` and IDE-like scans, not just a
library listing that bypasses these requests.

An outstanding upstream request must not occupy every transport dispatch worker.
Use deferred replies or another bounded mechanism that releases dispatch capacity
while hydration waits. Bound pending requests and memory, reserve capacity for
already-ready paths, and define timeout, cancellation and shutdown semantics.
Test more stalled stat/read requests than the configured worker count while
unrelated prepared directories and control operations continue to respond.

**5. Critical unresolved choice: exact sizes on first contact**

Git tree objects supply names, modes and object IDs, but not file sizes. A
blobless fetch therefore cannot by itself provide a fully stat-ready filesystem.
`readdir` names, `ls -l`, and an IDE's initial metadata walk are different startup
milestones. Returning a guessed size would violate filesystem correctness.

The protocol defines `object-info` for size queries. A live GitHub advertisement
checked during planning offered shallow and filtered fetches but did not advertise
that command. Capability discovery must govern its use; it cannot be assumed.
See the [Git protocol specification](https://git-scm.com/docs/protocol-v2).

Select the exact-size source by capabilities and configured API policy:

| Choice | Consequence |
|---|---|
| Advertised Git `object-info` | Batch size requests without fetching contents; unavailable in the observed GitHub advertisement. |
| Optional authenticated GitHub tree API | Recommended metadata accelerator if enabled: persist sizes and amortize requests across readers. Token availability and quota are real prerequisites for sustained use. |
| Git protocol only / no API budget | Batch-fetch blobs for the directory being statted, prioritizing demand over background snapshot download. A recursive stat scan ultimately requires all missing snapshot blobs. |

Do not make sustained operation depend on anonymous API quota. If the optional
API path is enabled, share its budget with namespace enumeration across all
repositories/readers, honor rate-limit responses and secondary throttling, request
gzip, and use Git protocol for file contents. A token does not change public-only
repository scope. The default API policy remains an explicit decision in section 13.

GitHub's tree endpoint includes blob sizes. Rely on `truncated`, not a hard-coded
entry/byte threshold; incomplete responses are never proof of complete metadata.
Use authoritative names, modes and IDs from Git trees. Query by the pinned tree
ID, reconcile API entries against that tree, and rebuild/hash API subtrees if
reusing their claimed completeness. This validates membership, not blob sizes.
Partition further requests by subtree and reuse known sizes by blob identity.
For root `ls -al`, prioritize a non-recursive root request rather than waiting
for a complete recursive response. See
[GitHub tree API documentation](https://docs.github.com/en/rest/git/trees).

Record API size provenance separately from sizes measured from actual blobs.
An API size is not authenticated by the Git tree hash. When contents arrive,
compare their actual length before serving them. A mismatch quarantines that
size observation, records a durable error and makes affected operations fail
with EIO until corrected metadata can be published and cached attributes safely
invalidated (or the mount reopened). Never silently truncate contents or retain
known-wrong sizes. This targeted check does not add a whole-import verification pass.

Ownership follows mount configuration; timestamps follow a documented snapshot
policy, since Git trees do not provide per-file mtimes. Directory sizes/link
counts are filesystem-defined. These policies must not require traversing history.
Symlink targets still require their blob contents when `readlink` is requested.
Do not assume small-blob filters capture every symlink or provide missing sizes.

**6. Durable filesystem metadata representation**

Use an immutable, paged directory hierarchy, with structural sharing between
snapshots. Keep records independent of absolute paths so an unchanged subtree
can be reused after a rename. The mount derives inode identity from the path.

A directory entry contains its name, Git mode/type, object ID, exact size when
known, and a child-directory reference where applicable. Attribute availability
is explicit. Completed scan-ready pages contain everything needed for directory
enumeration and stat without looking up blob descriptors or reconstructing Git
trees. File payload locators remain in a separate object index.

Compare inline object IDs with compact references into a separate content mapping:
stat does not need a full object ID, but moving IDs must not add a lookup per
entry during scanning. Use Buf-generated protobuf envelopes; benchmark a versioned
flat payload inside the envelope for scan-hot records that can be read directly
from mmap without allocating a Go object per entry. Define bounds and encoding
explicitly rather than replacing protobuf control/schema data with an ad hoc format.

Separate the unit of modification from the unit of transfer. Prototype small
immutable metadata pages around 4–16 KiB, initially 8 KiB, grouped into immutable
containers around 128–512 KiB, initially 256 KiB. Compress pages independently so
readers can fetch a page range or coalesce nearby ranges during scans. Keep root
bootstrap metadata small. These are tuning candidates, not fixed format constants.

Small adjacent directories can share pages. Large directories need sorted, paged
name indexes so one lookup or edit does not read or rewrite every sibling. A
change writes replacement pages into new containers; it must not copy unrelated
pages merely to refill a 256 KiB container. Publish underfilled containers when
needed rather than padding them or delaying a foreground publication to fill one.
Keep unmodified pages in their existing containers. Compaction can improve
locality later, with its cost measured separately.

Parents should carry direct location information for prepared children; a cold
walk must not pay another global tree-ID index lookup for every directory.
References should locate a page by immutable container identity and byte range;
records within a page can use local references. Build external references
bottom-up and avoid self-hashing reference cycles. Indexes mapping tree IDs,
object IDs, sizes and snapshots must themselves support incremental page updates;
do not hide a whole-repository table rewrite behind a small directory change.
Retain a tree-ID lookup index for reuse and unresolved children, but keep it off
the ordinary prepared-snapshot traversal path.

Early bootstrap records may name a child tree before its metadata block exists.
Preparing that child's pages adds a binding in a later publication; the initial
blobless fetch already supplied its Git tree. Completed directory
contents remain immutable; absence of a binding means unavailable, not absent.

Reader behavior:

- Fetch the blocks needed by current operations, deduplicating concurrent reads.
- During a scan, perform bounded read-ahead using child references and block
  locality, with explicit request and byte budgets.
- Decode into the existing global mmap cache; avoid a second persistent RAM
  cache or loading the entire index at mount time.
- Keep file contents completely off the metadata scan path once attributes are
  available. Instrument this as a regression invariant.

Logical sharing and physical locality compete: incremental pages may spread a
snapshot across containers from many publications. Measure cold scans after long
update sequences, not only immediately after initial packing. Compare the paged
hierarchy with a persistent ordered metadata index and a depth-first serialized,
content-defined chunking baseline before freezing the schema. Measure CPU work
as well as uploaded bytes: reserializing the entire snapshot to rediscover mostly
unchanged chunks is not an acceptable incremental update algorithm. Do not choose
a flat absolute-path layout without accounting for subtree rename amplification.

**7. Incremental upstream updates**

Use one repository-wide object pool and ingestion coordinator, replacing the
current model of a separate complete import for each revision.

1. Poll or explicitly refresh refs and capture a new ref observation.
2. Negotiate against the objects and history actually available. Fetch new packs
   and missing objects without recloning the repository.
3. Compare old and new root tree IDs. Equal tree IDs skip entire subtrees. Reuse
   known directory metadata by tree identity and known sizes by blob identity.
4. Build metadata only for changed directories and affected pages. Reuse moved
   subtrees; copy affected pages and necessary ancestor/index paths, and split
   oversized pages. Reuse unaffected pages without rewriting their containers.
5. Upload new immutable packs, object indexes, metadata and manifests before
   publishing their roots with CAS.
6. Make the new snapshot available without changing existing readers' commits.
   An explicit checkout changes the mount's snapshot pointer.

Handle force-pushes, tag movement and ref deletion as ref updates, not as reasons
to delete objects used by old snapshots. Treat renames as directory-entry changes
with subtree reuse; rename detection is not required for correctness.

The target for a one-file commit is work proportional to changed data, affected
directory pages and ancestor/index paths, rather than total snapshot entries or
history length. Index path depth may grow with repository size. Git tree objects
are not paginated, so fetching and comparing a changed high-fanout directory can
still cost its full tree size; measure that separately instead of claiming a
strict constant-time update.

For illustration, replacing four 256 KiB blocks per commit would produce about
500 MiB of uncompressed metadata over 500 commits. Four 8 KiB pages per commit
would instead produce about 15.6 MiB. Neither figure is a measured bound: count
index pages, splits, manifests, packing overhead, retained versions and compaction
as well. Compression savings do not excuse excessive rewrite work.

When one refresh receives 500 commits, retain their Git history but prepare
filesystem metadata for the requested tip and other actively requested revisions.
Do not automatically materialize 500 filesystem snapshots. Intermediate revisions
remain addressable and can have metadata prepared on demand from retained Git
objects. This is distinct from dropping history or changing the historical-blob
retention policy. Measure this batched case separately from 500 individually
published updates; both must preserve existing mounted snapshots.

Normal refresh should never require a full repack, full-snapshot serialization,
whole-history index rebuild or repository-wide size-table rewrite.
Metadata compaction can periodically combine fragmented blocks and remove costly
indirection. It publishes a new representation with identical snapshot semantics.
Old blocks remain available while readers can reference them. Garbage collection
and reader-retention policy are a separate prerequisite to physical reclamation.

**8. Background history and ingestion scheduling**

Use explicit priorities, with reserved capacity for foreground requests:

| Priority | Work |
|---|---|
| Foreground | Requested revision resolution, directory metadata, stat and file reads. |
| Near-term | Remaining metadata and contents for the active snapshot, plus bounded scan read-ahead. |
| History | Commit graph backfill, then other selected refs and historical trees. |
| Lowest | Remaining historical blobs and compaction. |

Use shallow deepening and filtering to acquire manageable batches. Commit-only
or treeless history requests can populate the graph before historical payloads,
subject to server support. Persist history frontiers and progress after each
usable batch. Do not make foreground work wait for a giant full-history transfer.
Bound background CPU, bandwidth, concurrent requests and staging space.

A normal fetch of unchanged refs does not necessarily backfill objects omitted
by earlier filters. Track availability and schedule explicit missing-object batches
or an appropriate refetch operation. Negotiate thin packs only when omitted delta
bases are available through the durable object index. Do not rely on disposable
staging files or evictable decoded data as the only copy of a required base.
Git's [partial-clone design](https://git-scm.com/docs/partial-clone) describes the
distinction between missing promised objects and complete local history.

Publish only usable batches with durable dependencies. Receiving bytes from a
large pack is progress, not proof that a history generation can be exposed.
Background failures preserve the working snapshot, record incomplete coverage,
and retry with backoff. A first-time partial mirror depends on upstream retaining
objects until ingestion finishes; force-push/GC failures must remain explicit.

Ingestion should stream new packs into durable segments with bounded staging and
disk-backed indexing. It must not require a complete local bare clone before
mounting. Preserve the existing efficient archive path where useful; avoid
reintroducing a whole-repository verification pass into the critical path.

Choose the ingestion engine before schema freeze. Start with the Git CLI as the
prototype staging engine: shallow/filtered fetches, explicit batched missing-object
fetches, deepening, and supported backfill/refetch commands. Check installed Git
capabilities. Measure staging disk, repeated negotiation and index costs. A native
protocol client and streaming indexer are an alternative only if measurements
justify their implementation cost; neither is assumed to come for free.

Both options need a repository-wide object index spanning multiple immutable
packs, incremental index publication, and an explicit policy for cross-pack delta
bases. Preserve durable base dependencies or resolve them during ingestion;
crash/restart and staging cleanup must not break recipes. Demonstrate adding a
second pack without rebuilding the first pack's index before freezing the format.

Local durable growth needs admission control independent of cache eviction.
Expose per-repository and aggregate durable usage, explicit repository removal,
and configurable ingestion capacity limits/free-space reserve. At capacity, pause
new ingestion with visible incomplete status; preserve published data and mounted
readers. Resume after space is made available. Never relabel history as cache or
silently evict it. Removal/GC must respect active readers before reclaiming objects.
Share Git fetch concurrency and bandwidth budgets across repositories as well as
the separate API rate budget. Casual browsing must not launch unlimited backfills.

**9. Publication, readers and the writer**

Use `HEAD` for the mutable current catalog manifest as in OBJECT_STORE.md, with
an immutable generation copy for retention/recovery; avoid adding another mandatory
GET merely to find the manifest. The new version of that manifest contains
roots for refs, snapshots, filesystem metadata, Git objects and history coverage,
plus resumable ingestion state. Large maps are paged structures, not inline
manifest contents. A publication can change availability without changing a
snapshot's commit or file bytes.

All readers use immutable roots for an operation or open directory enumeration.
A reader can adopt newer availability for the same commit between operations.
An open file retains its original content identity across checkout changes.
Directory cookies must not mix entries from different snapshots.

One coordinator serializes durable publication. Workers can fetch and stage
independent immutable objects concurrently. CAS failure requires rereading the
current manifest and reconciling work; an old history job must never overwrite
newer refs or discard another job's published availability. Crash recovery resumes
from published roots/checkpoints; unreferenced staged objects are not publication.

CAS protects publication but does not elect a writer. Initially enforce one local
coordinator per durable directory with an OS lock, and one explicitly deployed
cloud writer per repository prefix; mount instances route demands to it. Automatic
multi-instance writer election/failover is out of scope for the first version.
If that scope expands, design a renewable lease with fencing integrated into
publication before allowing takeover. An expired writer must not publish over
the new owner even if it rereads HEAD; a separate lease alone is insufficient.

Readers need object-store read permission only. Missing data is requested from
the writer through a small protobuf demand interface; readers must not acquire
write credentials or independently publish objects. On macOS this writer can
live inside the app; a cloud deployment can host it remotely. Coalesce demands
across readers, and allow an interrupted reader to detach from shared work.

The main module interfaces should remain small: request data availability,
refresh refs, open a pinned snapshot, and read its metadata/content. Hide fetch
negotiation, scheduling, retries, checkpointing and physical block placement
behind those interfaces. Retain the existing object-store seam.

**10. Kernel caching and checkout semantics**

Measure directory caching independently from the storage-format work. Permit
`FOPEN_CACHE_DIR | FOPEN_KEEP_CACHE` only for completed immutable directory views.
Keep mutable owner/repository listings and setup state uncached or explicitly
invalidated. Metadata arrival must not preserve a cached fake empty listing.

Changing checkout while preserving inode numbers requires reliable invalidation
of directory, attribute and file-content caches. The current experimental
vhost-user transport has notification limitations; audit the guest Linux virtiofs
driver and notification queue as well as the server. Do not assume adding a
server-side notification method proves the guest can receive it. The review's
claim that upstream Linux lacks this support remains a hypothesis to verify.
Current attributes use epoch mtimes and worktree opens use `FOPEN_DIRECT_IO`;
neither establishes automatic content invalidation on checkout. Benchmark those
choices independently of metadata layout before attributing the warm gap.
Do not change inode numbers to evade this requirement. If reliable invalidation
is unavailable, keep a mount revision-pinned while using aggressive kernel caches;
for switchable mounts prove conservative caching and change detection are correct
or leave switching unsupported on that transport pending a solution. Make that
limitation explicit rather than claiming the stable-inode switching requirement
has been met. Retain the target of supporting it.

Switching to prepared metadata should require selecting a new root, not walking
the tree. A previously unseen revision still has bootstrap cost. Avoid promising
instant checkout of every historical commit unless its metadata has been prepared.

**11. Migration and implementation sequence**

Implementation starts only after this design is reviewed.

| Milestone | Deliverable and gate |
|---|---|
| 1. Verify bootstrap and select ingestion engine | Repeat branch-tip and historical depth-one blobless fetches, including from GCE. Prototype Git CLI staging, missing-object batches and a second durable pack; compare a native client only if needed. Separate first names/stat/content, complete snapshot and history timings; verify API budget and size policy. |
| 2. Isolate the warm transport gap | Test directory caching, READDIRPLUS with unknown sizes, dispatch starvation and request/allocation counts. Audit guest/server invalidation together; preserve stable inodes. |
| 3. Prototype metadata layouts on existing data | Compare a paged directory hierarchy, ordered index and depth-first chunking baseline on medium and Linux-scale fixtures. Vary update-page and transfer-container sizes independently. Measure scans and amplification over 500 small commits, including batched refresh, individual publications and subtree renames. No new upstream fetcher required. |
| 4. Freeze protobuf schemas and publication invariants | Choose block/reference layout and completeness model from measurements. Add CAS/crash/concurrency tests before enabling writers. |
| 5. Add incremental metadata building | Produce new snapshots from changed trees, preserving old roots and shared blocks. Validate against ordinary Git checkouts. |
| 6. Add progressive bootstrap and demand ingestion | All-tree depth-one blobless bootstrap, exact-attribute policy, batched hydration, complete-current-snapshot target, NOTICE transition, deferred replies, cancellation and retry. |
| 7. Add resumable history and ongoing refresh | Priority scheduling, frontiers, eventual completeness, force-push handling and foreground isolation. |
| 8. Migrate and validate at scale | Medium fixture first, then Linux; real GCS and nested KVM, multiple readers and ongoing updates. |

Use a new format/publication version. Keep existing readers and durable stores
available during development. Build new metadata from retained objects where
possible instead of forcing another clone. Migration to repository-wide storage
must explicitly handle existing per-revision stores and retain rollback roots.
Do not remove or rewrite the current native Git view implementation as part of
this design; define its interaction separately before switching production mounts.

Account for the existing format-8 components explicitly:

| Component | Migration direction |
|---|---|
| Native packs and tree recipes | Reuse retained object bytes where possible; add multi-pack durable addressing and incremental object indexes. Remove tree reconstruction from prepared filesystem scans. |
| Per-generation global size table | Replace new-format writes with a repository-wide, incrementally paged size index. Retain the old reader for existing generations. |
| Converted directory pages | Reuse as migration inputs; replace new-format layout only after page/container benchmarks. |
| History index and changed-path Bloom filters | Preserve semantics and existing data where compatible; add incremental graph/frontier publication, with no whole-history rebuild per update. |
| Conversion-mode reuse | Carry forward unchanged-object/subtree reuse; do not regress it while replacing full archive-generation rebuilds. |

Audit existing repository RAM caches during migration against the single global
mmap cache requirement; decoding bounds must not become unbounded retained copies.

**12. Acceptance tests and performance gates**

Keep three measurements distinct: an unseen upstream repository, a prepared
snapshot in object storage with empty decoded cache, and an existing decoded
cache. A fast prepared mount is not evidence of fast first-time ingestion.

- For prepared snapshots, retain the goal of at most 2× the matched ordinary
  checkout scan baseline through virtiofsd, for both names and per-entry stat,
  on first and repeated scans. Also report guest-local disk separately.
- Budget dependent remote round trips on the critical path, transferred bytes,
  concurrency and total requests together. Trace actual dependency chains; dividing
  elapsed time by request count alone does not prove serialization. Select budgets
  that meet the elapsed-time target at measured GCS latency, rather than treating
  a total request count such as "tens" as sufficient.
- Time first root names, first exact root attributes, deep-path browsing and
  first file read separately. Target roughly the measured 1.04-second name-ready
  baseline and 23.23-second complete-current-snapshot baseline on comparable
  hardware/network, including indexing, metadata building and durable publication.
  These are engineering targets, not promises for arbitrary networks. Report
  fetch, upload, preparation and publication components; history must not gate
  first use. Repeat from GCE and test historical revisions, not just branch tips.
- No file payload fetches during a scan of a metadata-complete snapshot. Root
  lookup and mounting of a prepared snapshot must not enumerate the entire
  snapshot or history. First-use writer acquisition of all snapshot trees is
  distinct from forcing each reader to load them before its first listing.
- Show update cost for one changed file, widespread edits, a subtree move and
  a force-push: elapsed time, fetched bytes, new durable bytes, reused blocks and
  publication latency. Small updates must not rebuild the whole snapshot.
- Run 500 small one-file commits on Linux-scale metadata, both repeatedly editing
  one directory and spreading edits across directories. Compare 500 individual
  publications with one refresh preparing only the final tip. Include edits in
  a high-fanout directory. Report per-update latency (including tail latency),
  cumulative CPU, Git transfer bytes, metadata/index pages read and written,
  uncompressed metadata bytes, actual uploaded bytes, object-store request counts,
  and retained durable bytes. Account for manifests and compaction separately.
- Repeat empty-cache and warm scans after those 500 updates, before and after
  compaction. Small write amplification must not create unbounded scan indirection
  or sacrifice the scan performance goal. Demonstrate no full-snapshot walk,
  serialization, historical-pack rewrite or whole-index rebuild on a small update.
  Select numeric amplification budgets from these prototypes before schema freeze;
  the illustrative 15.6 MiB figure above is not an acceptance threshold.
- Run multiple read-only instances while ingesting and publishing. Check exact
  contents/attributes, stable inodes, pinned revisions and directory cookies.
- Inject crashes before/after uploads and CAS, retries, missing objects, cancelled
  callers, API throttling, unsupported filters and interrupted pack transfers.
- Test API size mismatches, anonymous/no-token operation, exhausted shared quotas,
  more blocked hydrations than transport workers, durable-capacity exhaustion and
  resume. Verify known-ready paths still respond and no wrong attributes are cached.
- Prove incomplete metadata is never exposed as missing/empty data. Verify that
  old mounted snapshots remain readable after updates and compaction.
- Evict the decoded cache during activity, verify the single global limit, and
  show that eviction never deletes durable repository data or ingestion state.
- Compare ingestion and storage overhead against the current importer. Do not
  assume that materializing metadata for every historical tree is cheap.

Tests must assert intended correctness and fail on regressions. Keep repeatable
fixture directories ignored and reuse existing clones. Use small protocol and
metadata experiments before expensive full-repository runs, with explicit runtime
cutoffs. Flag operations over one second. Delete all ad hoc cloud resources and
verify their absence after each cloud experiment.

**13. Decisions still open**

- Whether the optional authenticated GitHub tree API accelerator is enabled by
  default when credentials are available. Git-only operation remains supported,
  with directory-scoped blob batches and current-snapshot download for exact sizes.
- Whether eventual mirroring automatically includes every historical blob, or
  whether complete commit/tree history plus durable on-demand blobs is sufficient.
- Whether to proactively prepare additional historical snapshots beyond the
  requested tip and actively requested revisions; default to on-demand metadata
  for intermediate commits rather than building a snapshot for every commit.
- Metadata page size, container size, clustering and compaction policy, selected
  independently using milestone 3's scan and incremental amplification results.
- The transport mechanism for reliable cache invalidation during live checkout
  switching, and the remote demand interface between readers and the writer.
- Final ingestion-engine choice after the Git CLI prototype, durable-capacity
  defaults, and reader retention/removal rules. Native Git protocol implementation
  and distributed writer failover are not prerequisites without evidence or scope.

Native `git log`, `.git` shallow/promisor presentation and other native Git
commands are deliberately deferred. Their behavior must not determine the core
filesystem storage format in this planning round.

**14. Initial local implementation checkpoint (2026-09-27)**

The macOS GitHub mount now selects the progressive prototype. Its separate
`repositories-progressive-v1` durable namespace preserves existing imports. The
prototype acquires depth-one blobless trees, fetches root blobs for exact sizes,
then publishes the root before background snapshot and history acquisition.
Snapshot metadata uses protobuf pages in 256 KiB containers; the object index
uses incremental copy-on-write updates and CAS publication. Decoded objects use
the existing globally bounded mmap cache. Native `.git` compatibility remains
deferred on this path.

Local verification covers file equality with Git, pinned old/new snapshots,
publication conflicts, and reading after removing the acquisition repository.
A one-file update in a 160-directory fixture wrote 31,349 metadata/index bytes.
Importing the existing depth-one Linux pack locally took 0.78 seconds, metadata
preparation 3.09 seconds, and an in-process scan of 102,326 entries 1.19 seconds.
These are local prototype measurements, not fresh network acquisition or remote
scan acceptance results. A mounted Linux smoke check compared directory names,
types and blob sizes in four directories, plus contents of four files, against
Git at the same revision.

This is the first mountable slice, not completion of the milestones above.
Remaining work includes foreground priority over an active background fetch,
automatic background retry, durable-capacity policy, eliminating retained Git
pack duplication, remote acquisition coordination and GCS deployment, the
500-commit amplification benchmark, remote scan tuning, and compaction/retention.
The current reader also limits individual decoded objects to 64 MiB; large-file
streaming must be implemented before treating this format as general-purpose.
Full commit/tree history is downloaded in background; historical blobs are
currently acquired only when requested.
