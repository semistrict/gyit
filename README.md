# gat

A Go prototype for importing Git history into S3-compatible object storage and
mounting any imported commit as a read-only Linux filesystem. Many instances can
read while one writer publishes updates. Each mount can switch commits without
materializing a checkout; a path keeps its inode number across switches.

The ordinary `gat import` command imported a complete Linux repository with
**11,839,497 non-tag objects** in **90.9 seconds**, producing **20.43 GB** of local
object-store data. The source was an existing local clone, and persisted-store
verification ran separately after the timed import. See
[correctness results](CORRECTNESS.md) and [benchmarks](BENCHMARKS.md) for the
measured scope, operations over one second, and latest results. Live remote S3
performance remains unmeasured.

Structured metadata uses **protobuf**, with source schemas under [`proto/`](proto)
and Go code generated by Buf. Ordinary `go build` includes the archive importer
and readers. Archive imports write format **8**; reachable-object conversion
writes format **6**. Existing formats 4, 5, 6, 7 and the previously published
9015 development format remain readable. Older executables cannot open format 8.
Existing mounts keep their immutable generation during later imports.

## Use

Requires Go 1.26.6 or newer and Git 2.36 or newer on the importer. The default
cgo build uses the system zlib library and needs a C compiler and zlib development
headers. `CGO_ENABLED=0 go build -o gat ./cmd/gat` provides a pure-Go fallback
build. Linux mounts require
`/dev/fuse` and `fusermount3` (usually provided by the `fuse3` package). Readers
do not need the source repository or Git installed.

```sh
go build -o gat ./cmd/gat

# All local refs and HEAD; qualified archive imports also retain unreferenced objects.
./gat import --repo /path/to/linux --store s3://my-bucket/linux --region us-east-1

# Use a full commit ID. The mount command stays in the foreground.
mkdir -p /tmp/linux-mount
install -d -m 700 "$HOME/.local/run/gat"
./gat mount --store s3://my-bucket/linux --region us-east-1 \
  --sha FULL_COMMIT_SHA --cache-mib 32 \
  --socket "$HOME/.local/run/gat/control.sock" /tmp/linux-mount

# In another terminal, put the built client on PATH, then enter the mount.
# Run the export from this source directory. Other mounts keep their current SHA.
export PATH="$PWD:$PATH"
cd /tmp/linux-mount
gat status
gat switch main
gat switch HEAD~3
gat switch -
cd -

# Re-run import after fetching updates in the source Git repository.
./gat import --repo /path/to/linux --store s3://my-bucket/linux --region us-east-1

fusermount3 -u /tmp/linux-mount
```

Use `--endpoint https://s3.example.com --region REGION` for another S3-compatible
service. Credentials come from the standard AWS SDK credential chain. The bucket
must already exist. Use a dedicated prefix for each repository. Writers need
GetObject and PutObject; mounted readers need only GetObject. Mounts never LIST
the bucket. The service must support strongly consistent reads, exact byte-range
GETs, and conditional PutObject with `If-Match` / `If-None-Match`.

A local directory implements the same storage interface for development:

```sh
./gat import --repo /path/to/repo --store /tmp/repo-objects
./gat ls --store /tmp/repo-objects --sha FULL_COMMIT_SHA
./gat cat --store /tmp/repo-objects --sha FULL_COMMIT_SHA path/to/file
```

`import --rev REF` limits the import to that commit and its ancestors.
`--temp-dir /scratch` selects disk space for import staging. Shallow sources
import only their available history through the conversion path. Importing never
fetches, repacks, or changes source objects. The importer chooses its mode
automatically and prints the selected mode and any fallback reason on stderr.
`repo.Stats` exposes the same information as `ImportMode` and `FallbackReason`.

## Log

From a mounted repository or any subdirectory:

```sh
gat log
gat log --oneline -n 50
gat log --first-parent -n 20 main
gat log -n 5 HEAD~100
gat log README.md
gat log main -- docs/
gat log -- deleted-file
gat log --follow -- src/file.go
gat log -- ':(glob)src/**/*.go' ':(exclude)src/generated/**'
gat log -- ':(icase)README*'
gat log -- ':(attr:language=go)**'
```

The default is 20 commits; `-n`, `-N`, and `--max-count` select 0..1000.
An omitted revision starts from this mount's selected commit. An explicit branch,
tag, or revision uses the latest imported refs. Log never switches the mount.
Commit details are loaded from immutable metadata pages on demand, then streamed
one entry per protobuf frame. A running log keeps its starting commit and catalog
when another client switches or an importer publishes an update. Ordinary path
filtering reads metadata only. Edited-rename detection reads candidate contents
on demand; attribute filters read tracked `.gitattributes` files. Merge traversal uses committer-date priority and
suppresses shared ancestors; `--first-parent` follows one line of history.

File and directory pathspecs filter commits using Git's default history
simplification: a merge unchanged against a parent follows only that parent.
Paths are relative to the current directory inside the mount. Use `--` for deleted
paths or to disambiguate a path from a branch of the same name; with an explicit
`--socket` outside the mount, paths are repository-relative. File history reuses
the changed-path index to skip unchanged ancestry while keeping the cache bounded.
Directory filters, wildcard filters, and stores without that index use exact tree
comparisons. Pathspecs support ordinary wildcards and `top` (`:/`), `literal`,
`glob` (including `**`), `icase`, `exclude` (`:!` / `:^`), and `attr:` magic.
Exclusions are applied after positive matches; exclusions alone select from the
whole repository. Quote patterns so the shell does not expand them first.
Attribute requirements use the mounted checkout's tracked `.gitattributes`,
including nested rules and root macros, even when viewing older history. Global
Git configuration, `.git/info/attributes`, and custom diff drivers are not imported;
attribute matching follows the mount's case-sensitive filesystem semantics.
See [Git pathspec syntax](https://git-scm.com/docs/gitglossary#def_pathspec).

`--follow` accepts one literal file (including `top` and `literal` magic), follows
exact renames and copies through metadata, and detects edited renames using Git's
default 50% content-span similarity. It handles regular files, binary contents,
CRLF, empty files, and exact symlink renames. Default follow traversal omits merge
commits; `--first-parent` uses their first-parent diff. Git's rename-score flags
and custom diff drivers are not exposed. Exact rename detection reads no file
payload. Similarity checks stream 64 KiB blocks into fixed-size histograms and
fail explicitly if a request would read more than 256 MiB of candidate contents.
Attribute rules are limited to 4 MiB per evaluated path. Neither operation creates
a local checkout or retains a full tree. See [Git log](https://git-scm.com/docs/git-log).

Output follows Git's default author/date/message layout, or abbreviated ID and
subject with `--oneline`. Interactive terminal output opens `less` with `LESS=FRX`
when `LESS` is unset: short output exits automatically, and `q` closes the pager.
Pipes, redirects and `TERM=dumb` bypass paging. `GAT_PAGER`, then `GIT_PAGER`,
then `PAGER` can override the pager (shell commands/flags are supported); an empty
value or `cat` disables it. A missing default `less` falls back to direct output.
Interactive log output is fetched into a private temporary file before paging,
then piped to the pager. Reading the pager has no network timeout. The spool is
capped at 256 MiB and removed on exit; it contains log text only. Redirected
output continues to stream directly.
This version has no graph, revision-range filtering, ref decorations, mailmap
rewriting, or encoding conversion. The importer retains
up to 24 KiB of each message and 4 KiB of author identity; larger values are
explicitly marked truncated. Raw non-UTF-8 bytes are stored unchanged. Traversal
also bounds its merge frontier to 4096 pending commits, retains at most 100000
visited candidates with a 16 MiB key budget (unchanged graph steps do not need a
visited entry), and refuses individual
commits with more than 512 parents. These limits keep readers bounded even for
unusual histories. Reimport adds log metadata. Archive imports rebuild a complete generation;
reachable-object imports into older stores can reuse their existing file data. Readers need neither Git nor the source clone.

For a repeatable comparison with native Git using the existing ignored medium
fixture and demo store (no clone or import):

```sh
GAT_MEDIUM_LOG_TEST=1 go test ./internal/controlcli -run '^TestMediumLogMatchesGit$' -v -count=1
```

## Diff and blame

```sh
gat diff                       # empty: this mount is a clean, read-only checkout
gat diff HEAD~1                # compare an older revision with the mounted commit
gat diff main release -- src   # compare two revisions, filtered to a directory
gat diff main..release --name-status
gat blame README.md
gat blame -L 10,40 HEAD~5 -- README.md
gat blame --first-parent --line-porcelain README.md
gat annotate README.md
```

`diff` accepts zero, one, or two revisions, or `A..B`. The two endpoints use one
published catalog and remain pinned during concurrent imports or switches.
It prunes identical tree IDs, pages changed directories, and reads changed file
contents only when producing a patch. `--name-only` and `--name-status` require
no file contents. Changed paths are emitted in Git's byte ordering. `-U N` / `--unified N`
select 0..100 context lines (default 3). Text patches include additions, deletions,
mode/type changes, symlinks and submodule IDs; binary changes are reported without
embedding a binary patch. Text hunks use Myers' edit algorithm and Git-style indent heuristics; default
identifier-style hunk labels are included. Renames
appear as deletion plus addition (`--no-renames` is accepted explicitly).
Three-dot merge-base diffs, stats, attributes/text conversion, external diff
programs and whitespace options are not implemented.

`blame [REVISION] -- FILE` attributes each line to the commit that introduced it,
including lines inherited through different parents of a merge. The default
revision is the mounted commit. `annotate` shows the same attribution with tab
separators. `-L START,END` restricts the output to an inclusive numeric line range.
`--line-porcelain` includes full commit IDs, original/final line numbers, author,
author and committer timestamps/timezones, summary, path, previous-record
metadata, and content. Older stores lacking committer fields require reimport
for this output. This version follows the same path through
history: it stops at renames and does not detect moved/copied blocks, apply
mailmaps or honor attributes. Repeated-line ties can differ from native Git's
heuristics. No Git binary or source clone is required by readers.

Paths after `--` are literal file paths or directory prefixes, not Git pathspecs.
They are relative to the working directory inside a mount. With an explicit
`--socket` outside that mount, use repository-relative paths. Commands never
change the selected checkout.

History work buffers are bounded separately from the configured FUSE cache.
Patch/blame inputs are limited to 8 MiB and 100,000 lines per file; blame output
lines are limited to 24 KiB. The edit trace has a 2,097,152-integer budget, and
blame allows at most 100,000 candidate commit visits, 4096 pending history tasks and 512
parents per commit. Limits produce errors, never approximate attribution.
Two diff/blame requests may compute concurrently; others wait without blocking
filesystem reads or switching. They have a five-minute server deadline and a
305-second client deadline; `--timeout` can shorten the latter. Disconnecting a
client cancels its work. No full checkout or persistent history cache is written
to disk by the server. Changed-path sorting uses at most 32 MiB of charged
metadata and 100,000 paths. The CLI spools normal blame output to a private,
automatically removed protobuf file (maximum 256 MiB) to align columns like Git.
Existing stores need the same metadata reimport described under Log.

New imports also build a compact history index: blocks of at most 256 commits
contain ordered parent positions, tree IDs and a 64-byte changed-path Bloom
filter. A negative filter skips the first-parent tree lookup; positives use the
normal exact comparison. Merges retain parent order, and false positives affect
only speed. Blame keeps one decoded block as a work buffer (at most 1 MiB on the
wire); encoded blocks share the existing 32 MiB cache. Unchanged commits skipped
by the filter do not consume the candidate-visit limit. No complete graph is
loaded, and old stores remain readable through the original walker.

Repeat the byte-for-byte command comparisons against the existing ignored medium
fixture and imported store. The suite builds the real binary, exercises the
protobuf control server, compares log, diff, blame, annotate and status after
switching, and removes its temporary Git worktree. Diff rename detection is
explicitly disabled on both sides. It never clones or fetches the source.
`GAT_PARITY_STORE` and `GAT_BENCH_STORE` can select a different imported store:

```sh
GAT_MEDIUM_PARITY_TEST=1 go test ./internal/controlcli -run '^TestMediumCommandParity$' -v -count=1
# Same snapshot and 32 MiB cache, with and without the history index:
go test ./internal/repo -run '^$' -bench '^BenchmarkBlameMedium$' -benchtime=1x -count=3
```

## Import modes and compression

The default importer automatically retains a native Git pack when the source is
SHA-1, contains one complete pack with its index, has no loose objects, alternates,
shallow boundary, promisor packs, grafts, replacement refs, or relevant Git
history/object-directory overrides, and at least two workers are available.
`--rev`, `--no-deltas`, or explicit `--delta-depth` / `--delta-candidates` settings
select reachable-object conversion instead. Unsupported pack metadata also
falls back to conversion. Malformed data and I/O failures are errors.

Selection belongs to one import's context; no experimental environment switches
or special build command are needed. A missing Git `.rev` reverse index is built
only in temporary staging space from the existing `.idx`; the source is not
rewritten. The current native planner handles at most 12 million source objects.
Sources outside its supported shape use the conversion path and report why.

Archive import copies the source pack once into immutable 64 MiB segments.
It reuses Git's existing zlib frames and delta chains, stores bounded protobuf
read recipes, and emits catalog rows in object-ID order. Accepted blobs and trees
are not reconstructed or recompressed during import. Metadata parsing and bounded
admission checks still run; object contents are authenticated when read. Commits,
large files, and objects whose native recipes exceed read limits use bounded
conversion work. The catalog includes every source-local commit, tree, and blob;
its history index contains commits reachable from the captured refs. Tag bodies
are not exposed as original Git objects.

Reachable-object conversion uses pure-Go `klauspost/compress/zstd` at
`SpeedFastest`. Files are split into 1 MiB chunks, stored either as full frames or
Zstandard-compressed protobuf copy/literal deltas. Delta depth defaults to one
and accepts `--delta-depth 1..8`; up to four candidates per path/chunk are examined
by default (`--delta-candidates 1..8`). A delta must save at least 20% after a
200-byte allowance per dependency. `--no-deltas` selects independent frames.
These explicit options affect new conversion output, not the native recipes
retained by automatic archive import. They do not repack existing generations.

The default cgo build uses native **zlib** to decode Git frames and bounded delta
metadata; the no-cgo build uses Go's zlib implementation. This is separate from
the earlier native **Zstandard** encoder experiment, which did not meet the
required greater-than-2x improvement and was not adopted. To benchmark the
conversion encoder on the existing medium fixture:

```sh
go test ./internal/repo -run '^$' -bench '^BenchmarkCompressorFixture$' -count=3
```

## Storage and demand loading

| Data | Archive format 8 | Conversion format 6 |
| --- | --- | --- |
| File bytes | Copied native zlib frames and bounded recipes; fallback chunks for inadmissible objects | 1 MiB Zstandard chunks with optional bounded deltas |
| Directories | Native tree recipes decoded on demand, or compressed directory pages | Compressed directory pages |
| File sizes | One bounded global size table | Sizes embedded in directory entries |
| Blob lookup | Separate direct index keyed by binary object ID and part number | Chunk records in the main catalog |
| Commit, refs, history metadata | Immutable protobuf index pages | Immutable protobuf index pages |
| Publication | Immutable generation manifest, then atomic replacement of `HEAD` | Same |

Index references contain a pack key, offset, length, and page checksum. Main
index pages contain at most 128 records or child pointers and are batched into
8 MiB immutable packs. Readers issue byte-range GETs for the required pages;
they do not download an index pack or ask the store to LIST a prefix. See
[the object-store layout](OBJECT_STORE.md) for records and read bounds.

Opening a format-8 snapshot reads its catalog paths and loads the bounded global
size table. Root `ls` then reads only the root directory's metadata or archived
tree ranges. It does not read file bodies or walk descendant directories.
`ls -l` obtains file sizes from the table, and entering a subdirectory loads that
directory on demand. Native trees larger than 64 KiB, or whose recipes exceed
read limits, are converted into directory pages of at most 128 entries, with a
64 KiB decoded-page cap.

Native blob recipes admit nonempty files up to 1 MiB. Each recipe has at most
64 frames, an 8 KiB description, 3 MiB of fetched compressed data, and 4 MiB of
reconstruction work. Blob recipes admit at most four byte ranges; tree recipes
admit at most sixteen. At most four range requests run concurrently per recipe.
Readers verify reconstructed Git object IDs and reuse verified cached bases.
Larger files use independent 1 MiB chunk addressing, so a partial read need not
fetch the entire file. Conversion delta chunks need at most depth + 1 payload
GETs; embedded dependency ranges avoid walking history to locate bases.

The default retained-data cache budget is **32 MiB**, not a process RSS limit.
Format-8 stores require at least 32 MiB configured. They reserve 16 MiB for a
single generation's global size table, including its owned lookup metadata, and
use a shared 16 MiB LRU for other retained data. Views and snapshots share this
reservation; switching generations replaces the table in the same slot. The
current format-8 implementation does not enlarge these two budgets when a larger
cache is configured. Older conversion stores use the configured LRU budget and
permit `--cache-mib 0`. Cache bookkeeping, bounded in-flight decode buffers,
query work buffers, FUSE inodes/handles, and the Go runtime consume extra memory.
Readers write no checkout or persistent data cache to local disk.

Import staging is separate from the reader cache. It uses temporary mapped
metadata tables, bounded queues, external sorting where needed, and pack upload
buffers. `--temp-dir` selects its disk location; `--workers` selects concurrency
(default at most four available Go execution threads). History indexing overlaps
object conversion. Publication waits for every producer and upload; cancellation
joins source processes and workers before removing owned scratch files.

An archive update currently rebuilds a **complete immutable generation**, including
its archived pack and indexes, then publishes with the starting `HEAD` token.
It does not reuse the previous archive generation incrementally. Conversion
imports into formats 4–6 can reuse prior blobs and index subtrees and add only
new reachable history. Switching from an archive store to conversion also builds
a complete replacement. Both modes preserve existing readers and use atomic CAS.

## Concurrency and checkout semantics

Readers pin immutable catalog roots. The writer uploads packs, uploads the new
catalog, writes a generation manifest, and **only then** replaces `HEAD` using
compare-and-swap. Failed imports cannot change an existing reader's view. A
conflicting writer fails publication rather than silently overwriting another
generation. Initial publication uses create-only CAS; updates compare the token
read with the starting `HEAD`. An existing `HEAD` without a usable token is rejected
before uploads. Local storage holds an inter-process file lock across comparison
and atomic rename; S3 uses `If-None-Match: *` / `If-Match: ETag`. An S3-compatible
service must enforce these conditions atomically and provide strong consistency.
There is no unconditional fallback or automatic overwrite retry. Re-run a losing
import to rebuild against the latest publication; its staged objects may remain
unreferenced until garbage collection is implemented. A transport failure after
publication may have an ambiguous outcome: inspect the latest publication before
retrying. This protects competing importers but does not schedule writers or merge
conflicting source refs.

The mode-0600 control socket lives outside the checkout in a private (0700)
directory. From the mount or any subdirectory, `gat status` prints Git-style
clean-checkout status (branch name or detached HEAD), and `gat switch REVISION`
switches only that mount. The client walks up
from its physical working directory to the nearest root carrying the
`user.gat.control` extended attribute, a protobuf `MountEndpoint` with the socket
address. The attribute and status RPC require no object-store reads; normal
filesystem path resolution may read directory metadata. No hidden file or
reserved path is added to the checkout. An explicit `--socket PATH` overrides
discovery, including when called outside the mount. Invalid endpoint attributes
fail at that mount rather than silently selecting another ancestor.
Supported targets include branches, qualified refs, tags (including annotated
and nested tags), unique abbreviated object IDs, `HEAD`, `@`, ancestry chains
such as `HEAD~3^2`, and commit peeling (`^{}` / `^{commit}`). A unique remote
branch can be addressed without its remote prefix. `HEAD` means this mount's
current commit; `-` and `@{-1}` restore the previous checkout, including its branch
or detached identity. Previous checkout history lasts for the mount process. Branch names are case-sensitive.
`--sha REVISION` remains a legacy alias for the positional argument.

Refs reflect the last import; switching to a branch selects that imported tip
once, without continuously following it. Re-run import to refresh moved, added,
or deleted refs. Reimport also adds missing refs and parent metadata; whether
file data is reused depends on the import mode described above. Ref and parent pages are read on demand; readers still
need no source clone. Revision syntax follows the relevant forms in
[Git's revision documentation](https://git-scm.com/docs/gitrevisions).

Status reports `On branch main` or `HEAD detached at <revision>`, followed by
`nothing to commit, working tree clean`. The mount is read-only, so this requires
no worktree scan. `--short`/`-s`, `--branch`/`-b` (including `-sb`),
`--porcelain[=1|2]`, and `-z` follow Git's clean-worktree output formats. In a clean
mount, short/porcelain status without `--branch` produces no output. Branch and
SHA are captured together, so status cannot mix identities during a switch.
Upstream/ahead-behind messages are not reported: source tracking configuration
is not imported. Status does not claim to implement mutable-worktree, index,
merge, or rebase state. See [Git status formats](https://git-scm.com/docs/git-status).

The command client needs neither Git, storage credentials, nor the source repository.
Status, switch and log default to a 35-second client timeout (`--timeout`) and a
30-second server deadline; diff/blame use the longer deadlines described above. Failed lookups leave the current version intact. Switch writers
are serialized while status requests and filesystem readers continue.

The protocol is defined in
[`proto/gat/control/v1/control.proto`](proto/gat/control/v1/control.proto): one
request per Unix connection, with one response for status/switch or a stream of
log entries, diff chunks or blame lines followed by an explicit end marker. Every message is framed with a
four-byte big-endian length and limited to 64 KiB. Envelopes carry protocol version 1, typed operations,
and typed errors. Up to 16 connections are handled concurrently. Oversized or
malformed frames are rejected, and shutdown cancels and joins active handlers.
This replaces the earlier newline protocol; old clients must be rebuilt. A lost
response can mean the switch already completed: query status before retrying.
Existing socket paths are never overwritten; after an unclean exit, verify the
old server is gone before removing its stale socket. Normal unmount removes it.

JuiceFS's local command channel was the reference: its commands open `.control`
and exchange binary messages with the filesystem. Here the channel is an
Unix socket discovered through a root attribute, with protobuf for both discovery
and requests, avoiding reserved names inside a Git tree.
See [LIMA.md](LIMA.md) for the local running demo and its commands.

A new checkout reads
`HEAD` and the requested commit's catalog path, then atomically swaps the mount's
snapshot pointer. It does not walk either checkout or invalidate a repository's
worth of cached nodes. Each operation captures one snapshot; concurrent
operations can straddle a switch. This is not a transaction across multiple
filesystem calls.

Inode numbers are deterministic 64-bit hashes of repository-relative paths,
independent of commit and file contents. An unchanged path keeps its number,
including a changed file. Renames change inode identity. Hash collisions are
theoretically possible. Open file handles keep reading their original version;
new opens see the switched version. Directory streams likewise retain their
selected version once enumeration begins.

Kernel entry/attribute timeouts are zero and files use direct I/O. This prevents
stale content at stable inode numbers after a switch; the userspace cache handles
reuse. It costs extra FUSE calls and currently excludes normal file-backed mmap
workloads. Do not assume this prototype can run every compiler or executable
directly from the mount.

## Limits

- No writes, Git network protocol, `.git` directory, branch management, garbage
  collection, resumable interrupted uploads, or retention policy. Failed imports
  may leave unreachable immutable objects. **Do not delete old generations,
  index pages, or packs while readers may use them.**
- Native recipes are limited by frame count, fetched bytes, and reconstruction
  work. Converted chunk deltas default to depth one and permit up to eight; their
  path hints and bounded matching can miss sharing across renamed files or shifted
  chunk boundaries.
- Compression overlaps with source reads and staging. Pack uploads remain
  sequential; long-distance S3 PUT latency can dominate publication. Caches are per mount; there is no shared fleet cache.
- File bytes, executable bits, and symlinks are preserved. Submodules appear as
  empty directories; Git LFS files remain pointer files. Ownership and timestamps
  are synthetic. Repository extended attributes and arbitrary directory seek cookies
  are not implemented; the mount root exposes only its control endpoint attribute. Names longer than 255 bytes are rejected.
- Revision resolution covers the forms listed above, not the entire Git command
  language. Source reflogs/date selectors, upstream/push selectors, merge-base
  ranges, commit-message searches, and path checkout are unsupported. Switching
  never fetches a missing commit or creates a branch. Direct `ls`/`cat` store
  commands still require a full commit SHA.

## Validation

Buf handles schema linting and Go code generation. The Go protobuf compiler is
pinned as a module tool, so no separate `protoc` or `protoc-gen-go` installation is
needed. Install the [Buf CLI](https://buf.build/docs/cli/installation/), then run:

```sh
buf lint
buf generate
```

Edit the `.proto` source and run `buf generate`; do not edit
`internal/gen/` directly. Index pages and manifests are hashed over their actual
protobuf bytes. Encoding is deterministic with the pinned schema/runtime.

```sh
go test -race ./...
go vet ./...

# Linux integration: real mounts, two readers, publisher, in-place switch,
# stable inode numbers, old open handles, removals, additions, and paged readdir.
GAT_FUSE_TEST=1 go test ./internal/mount -v

# Optional local S3 tests. Endpoint must be loopback. Test credentials are
# gat-test / local-test-secret; tests create and delete dedicated buckets.
GAT_S3_TEST_ENDPOINT=http://127.0.0.1:19000 go test ./internal/store -run TestS3 -v
GAT_S3_TEST_ENDPOINT=http://127.0.0.1:19000 GAT_SCALE_SOURCE=/path/to/linux \
  go test ./internal/repo -run TestExistingRepositoryS3 -v -count=1 -timeout=30m
```

The tests also cover SHA-256 repositories, non-UTF-8 names on Linux, chunk-boundary
reads, corruption detection, cache limits, incremental imports, failed publication,
concurrent old readers, and catalog updates across multiple index levels.

### Repeatable medium-repository test

Choose a GitHub repository with at least two commits on its default branch for
the first run. GitHub access uses `gh`; the clone is complete and bare, so no
checkout or blob filtering is involved.

```sh
# First run: clone once, then import and verify.
GAT_MEDIUM_TEST=1 GAT_CLONE_REPO=owner/repository \
  go test ./internal/repo -run '^TestMediumRepository$' -v -count=1 -timeout=45m

# Subsequent runs reuse the existing clone, without cloning or fetching.
GAT_MEDIUM_TEST=1 \
  go test ./internal/repo -run '^TestMediumRepository$' -v -count=1 -timeout=45m
```

The source lives at `.testdata/medium-repo.git`, covered by the root `.gitignore`.
A failed clone is never published into that directory. Move that cached clone
aside explicitly to select a different repository or download a newer fixture.
Tests never modify the original source checkout elsewhere on disk.

Each run imports all available history into a **fresh temporary local object
store**, checks the root listing without any file-content downloads, compares
every HEAD file's path/mode/object ID with Git, checks complete contents of a
deterministic sample of files using Git hashes, opens a historical commit, and
checks the publication and readback after an unchanged reimport. Import timings plus
read I/O counts are recorded. The opt-in test enforces a **five-minute import
budget**, excluding clone time and post-import verification. Set
`GAT_IMPORT_MAX_DURATION=10m` only when deliberately measuring a different
fixture or slower machine; read I/O bounds remain enforced. Set
`GAT_NO_DELTAS=1` for an independent-compression baseline. Set
`GAT_IMPORT_WORKERS=4` or `GAT_IMPORT_WORKERS=numcpu` to compare compression
concurrency while keeping the same fixture and fresh destination. The temporary
store is removed after the test; the ignored clone remains available for reuse.

Set `GAT_DELTA_DEPTH=1..8` and `GAT_DELTA_CANDIDATES=1..8` for individual
measurements. A sequential comparison reuses the clone and creates a fresh,
automatically cleaned destination for each setting:

```sh
GAT_DELTA_MATRIX=1 go test ./internal/repo -run '^TestDeltaMatrix$' -v -count=1 -timeout=30m
```

See [BENCHMARKS.md](BENCHMARKS.md) for measured scope and results.

### Full-history Linux measurements

Use the ordinary-build verification harness with the existing ignored full bare
clone. It never clones, fetches, or changes that source:

```sh
python3 scripts/verify_linux.py prepare --source .testdata/linux-repo.git
python3 scripts/verify_linux.py build
python3 scripts/verify_linux.py import --store .testdata/linux-store
python3 scripts/verify_linux.py catalog --store .testdata/linux-store
python3 scripts/verify_linux.py reader --store .testdata/linux-store
python3 scripts/verify_linux.py commands --store .testdata/linux-store
```

`prepare` reuses its independently hashed object inventory. Import requires an
empty destination and times the actual ordinary `gat import` executable, with a
180-second process-group watchdog, then verifies its publication independently.
The other phases reuse a published store, compare every catalog object against
Git's inventory, check sampled exact file and directory contents, and compare
98 command outputs and exit statuses with native Git. Reports retain failures,
source/store identity, physical store size, and operations over one second.

For mounted checks, build the same source normally on Linux and use the separate
two-mount FUSE verifier. It checks nested directories, read-only behavior, stable
inodes, pinned open handles, and isolated version switches, then removes its own
mounts and processes. Instructions and explicit limits are in
[scripts/VERIFY_LINUX.md](scripts/VERIFY_LINUX.md). These local-store results do
not establish remote S3 latency. A larger operation can exceed one second even
when root navigation and version switching remain small metadata operations.

Underlying contracts: [S3 GetObject byte ranges](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html),
[S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html),
and [go-fuse filesystem interfaces](https://pkg.go.dev/github.com/hanwen/go-fuse/v2/fs).

## Read-only object and history views

The same `gat` binary discovers the control socket from any directory in a mount:

```sh
gat show HEAD
gat show HEAD:README.md
gat ls-tree -rl HEAD
gat ls-files -s
gat cat-file -p HEAD:README.md
gat grep -n 'pattern' -- README.md
gat branch -a
gat tag --list 'v*'
gat show-ref --tags
gat rev-parse --short HEAD
gat rev-list --count HEAD
gat merge-base HEAD main
gat shortlog -sne HEAD
```

All commands stream through protobuf, pin one publication for all arguments,
retain the mount's selected HEAD, and leave the checkout unchanged. New imports
can advance named references while readers remain mounted. Branch/tag creation,
deletion, and renaming are rejected. `show` uses the same terminal pager as `log`.
`grep` with no matches, quiet missing-reference checks, and false
`merge-base --is-ancestor` return exit status 1 without a diagnostic.

`show` supports commits, blobs, trees, ancestor and `REV:path` selectors,
`--oneline`, `-s`, `--name-only`, `--name-status`, `-U`, pathspecs, and
`--first-parent`/`--dd`. Exact renames and unambiguous edited renames at 50%
similarity are detected. Ambiguous edited pairings or exhausted comparison
budgets request `--no-renames`; they do not guess. Default merge display works
when no combined patch is needed. Combined hunks are not implemented and request
`--first-parent`. Patch rendering has the same file-size and hunk-algorithm
limits as `diff`.

`ls-tree` supports recursion, directory entries, long sizes, name-only/name-status,
full-tree/full-name, and NUL output. `ls-files` lists the committed snapshot,
including stage and NUL formats; there is no writable index or untracked-file
scan. `cat-file` supports blob/tree content and object type, size, and existence.
Original commit/tag bodies are not exposed by this command: requests for those bodies fail
explicitly, as do tag-size queries. Commit/tag display metadata is not a
replacement for the original signed object. References peeling to trees or blobs are retained for object views; mounts and
version switches still require a commit. Reimport older stores to populate original annotated-tag IDs
and symbolic reference targets; this metadata upgrade is atomic.

`grep` supports basic/extended expressions, fixed strings, case-insensitive
matching, line numbers, counts, matching filenames, inversion, binary-file
handling, NUL filenames and pathspec filtering. It scans blobs on demand, keeping
one decoded chunk and a bounded line buffer. PCRE/backreferences are unsupported.
Broad searches currently scan file content, so a repeated scan larger than the
cache still fetches data again. There is no full-text index yet.

`rev-list` supports ordinary exclusions/two-dot ranges, counts, parents,
first-parent traversal, reversal and result limits. `merge-base` supports all
best common ancestors and ancestry checks. `shortlog` groups by author with
tracked `.mailmap` mappings and supports summary, numeric ordering and email.
Symmetric ranges, graph-command path filtering, and custom shortlog grouping or
formatting are rejected. Reference format atoms are a documented subset in the
command implementation; unsupported atoms and annotated-tag subject formatting
are rejected.

Reference lists have a 16 MiB metadata limit. Directory traversal retains at
most 16 MiB of active directory metadata. Graph membership uses compact bitsets
with an 8 MiB bound per set; older stores use a bounded fallback. These temporary
query buffers are separate from the shared 32 MiB data cache, and the daemon runs
at most two history/view queries concurrently. No full checkout is downloaded.

## Bounded import performance checks

These commands exercise directory-history amplification and blob worker scheduling
without starting another full-history import:

```sh
go test ./internal/repo -run '^$' -bench 'BenchmarkImport(Directory|Blob)History$' -benchtime=1x -count=3
```

For a focused comparison on real Linux directory contents, save the old binary
before rebuilding, then use the already-downloaded bare repository:

```sh
cp .build/gat .build/gat-before
go build -o .build/gat ./cmd/gat
python3 scripts/benchmark_linux_subset.py --source .testdata/linux-repo.git --baseline .build/gat-before --gat .build/gat --versions 512 --output .build/linux-subset
```

This creates a temporary linear history from the last 512 first-parent revisions
that changed `drivers/net`. It borrows source objects locally, does not clone or
fetch, and removes temporary repositories and stores after the comparison. Each
import is capped at 60 seconds. Reports retain timings, binary hashes, total store
bytes, sampled peak scratch-file sizes, and root-listing comparisons. Times over
one second are flagged. This is a subset benchmark, not full Linux history or an
S3 latency measurement. OS caches are not flushed.
